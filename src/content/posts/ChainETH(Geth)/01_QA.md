## Q1: How does `SetBytes` truncation work? Can it cause data loss?

`Hash.SetBytes()` and `Address.SetBytes()` in `common/types.go` handle inputs that don't match the target size:

- **Too long**: left-truncate, keeping only the rightmost bytes
- **Too short**: right-align and zero-pad on the left

```go
func (h *Hash) SetBytes(b []byte) {
    if len(b) > len(h) {
        b = b[len(b)-HashLength:]      // trim from left
    }
    copy(h[HashLength-len(b):], b)     // right-align copy
}
```

Example with `Address` (20 bytes) given 22 bytes input:

```
Input (22 bytes):  [AA BB 01 02 03 ... 19 20]
After truncation:  [01 02 03 ... 19 20]       <- AA BB discarded
```

Example with 3 bytes input:

```
Input (3 bytes):   [01 02 03]
Result:            [00 00 ... 00 01 02 03]     <- zero-padded on left
```

**In practice, truncation never triggers in normal usage.** The actual callers always pass data of the correct length:
- `Keccak256` output is always 32 bytes -> `BytesToHash`, exact fit
- `Ecrecover` recovers 20-byte addresses -> `BytesToAddress`, exact fit
- Data read from the database is stored at the correct length

The truncation branch is defensive programming, mainly guarding against `BigToHash` / `BigToAddress` where `big.Int.Bytes()` can return variable-length output. A `big.Int` that exceeds 32 bytes is not a valid hash anyway, so truncation is reasonable.

## Q2: What do the fork fields in `ChainConfig` mean (HomesteadBlock, BerlinBlock, etc.)?

Each field represents a historical hard fork's activation point. The value is the block number at which that fork's rules take effect.

| Field | Approx. Date | Key Change |
|-------|-------------|------------|
| `HomesteadBlock` | 2016.3 | Fixed contract creation gas calculation |
| `DAOForkBlock` | 2016.7 | Emergency rollback after The DAO hack (ETH/ETC split) |
| `EIP150Block` | 2016.10 | Raised gas costs for IO-heavy opcodes (anti-DoS) |
| `EIP155Block` | 2016.11 | Introduced ChainID for replay protection |
| `EIP158Block` | 2016.11 | Cleaned up empty accounts to reduce state bloat |
| `ByzantiumBlock` | 2017.10 | Added precompiles for zkSNARK support |
| `ConstantinopleBlock` | 2019.2 | Added CREATE2, bitwise shift instructions, reduced gas |
| `PetersburgBlock` | 2019.2 | Emergency rollback of EIP-1283 (reentrancy vulnerability) |
| `IstanbulBlock` | 2019.12 | Reduced calldata gas, adjusted storage opcode pricing |
| `MuirGlacierBlock` | 2020.1 | Delayed difficulty bomb |
| `BerlinBlock` | 2021.4 | EIP-2929: cold/warm access gas model |
| `LondonBlock` | 2021.8 | EIP-1559: base fee mechanism, gas market reform |
| `ArrowGlacierBlock` | 2021.12 | Delayed difficulty bomb again |
| `GrayGlacierBlock` | 2022.6 | Final difficulty bomb delay before The Merge |
| `MergeNetsplitBlock` | 2022.9 | The Merge: PoW -> PoS |

Post-Merge forks switch to **timestamp-based** activation (`ShanghaiTime`, `CancunTime`, ...) because PoS has a fixed 12-second slot interval, making wall-clock times more intuitive than block numbers.

For mainnet: `BerlinBlock = 12,244,000` means that when processing block #12,244,000, `IsBerlin()` returns true and cold/warm access gas rules take effect. Block #12,243,999 still uses the old rules.

## Q3: Does the EVM use the latest fork rules for all blocks?

No. **Each block is executed with its own era's rules.** When a new node syncs from genesis, it must re-execute every historical block. Using current rules on old blocks would produce different gas calculations, different execution results, and a mismatched state root — the block would fail validation.

At EVM creation time (`core/vm/evm.go:145`), the fork rules are determined from that block's number and timestamp:

```go
chainRules: chainConfig.Rules(blockCtx.BlockNumber, blockCtx.Random != nil, blockCtx.Time),
```

Then the appropriate instruction set is selected (`core/vm/evm.go:152-181`):

```go
case evm.chainRules.IsOsaka:
    evm.table = &osakaInstructionSet
case evm.chainRules.IsPrague:
    evm.table = &pragueInstructionSet
case evm.chainRules.IsCancun:
    evm.table = &cancunInstructionSet
// ... all the way back to Frontier
```

## Q4: Where are the fork rules stored?

There is no single centralized location. Fork rules are distributed across the modules they affect:

| Rule Type | Location | Example |
|-----------|----------|---------|
| Opcode instruction sets + gas | `core/vm/jump_table.go` | `newXxxInstructionSet()` per fork |
| EIP-1559 base fee calculation | `consensus/misc/eip1559/` | `CalcBaseFee()` checks `IsLondon` |
| EIP-4844 blob gas calculation | `consensus/misc/eip4844/` | `CalcExcessBlobGas()` checks `IsCancun` |
| Header validation rules | `consensus/beacon/` | `VerifyHeader()` checks different fields per fork |
| Transaction validation | `core/txpool/validation.go` | Accepts different tx types per fork |
| State transition rules | `core/state_transition.go` | Intrinsic gas uses different formulas per fork |

Each module checks `chainRules.IsXxx` to decide which logic to apply.

The instruction sets in `jump_table.go` are the most visible part. They are built via **layered inheritance** — each fork copies the previous fork's instruction set and adds/modifies entries:

```
Frontier -> Homestead (+ DELEGATECALL)
  -> TangerineWhistle (change BALANCE/SLOAD gas)
    -> SpuriousDragon (change EXP gas)
      -> Byzantium (+ STATICCALL, RETURNDATASIZE)
        -> Constantinople (+ SHL, SHR, CREATE2)
          -> Istanbul (+ CHAINID, change SSTORE gas)
            -> Berlin (+ EIP-2929 cold/warm gas)
              -> London (change refund rules, + BASEFEE)
                -> Merge (DIFFICULTY -> PREVRANDAO)
                  -> Shanghai (+ PUSH0)
                    -> Cancun (+ BLOBHASH, MCOPY, TSTORE/TLOAD)
                      -> Prague (+ EIP-7702)
                        -> Osaka (+ CLZ)
```

Each layer does one of three things: add new opcodes, change gas prices, or change behavior logic.

## Q5: What does `newOsakaInstructionSet()` do?

```go
func newOsakaInstructionSet() JumpTable {
    instructionSet := newPragueInstructionSet()  // 1. Copy Prague's full instruction set
    enable7939(&instructionSet)                   // 2. Add CLZ opcode (EIP-7939)
    return validate(instructionSet)               // 3. Validate integrity, return
}
```

`enable7939()` inserts a single new opcode `CLZ` (Count Leading Zeros) into the jump table:

```go
func enable7939(jt *JumpTable) {
    jt[CLZ] = &operation{
        execute:     opCLZ,
        constantGas: GasFastStep,     // 5 gas
        minStack:    minStack(1, 1),  // pop 1, push 1
        maxStack:    maxStack(1, 1),
    }
}
```

`opCLZ` counts how many leading zero bits a 256-bit integer has: `CLZ(0x00FF)` = 248 (256 - 8 significant bits).

So: **Osaka = all of Prague's functionality + one new CLZ opcode.**

## Q6: Why do post-Merge fork checks require `IsLondon`?

```go
func (c *ChainConfig) IsShanghai(num *big.Int, time uint64) bool {
    return c.IsLondon(num) && isTimestampForked(c.ShanghaiTime, time)
}
```

On mainnet, London is always activated before Shanghai, so the `IsLondon` check is technically redundant. But `ChainConfig` is a general-purpose struct — anyone can construct arbitrary configurations, including private chains and test chains.

The codebase includes `NonActivatedConfig` (`params/config.go:339`) where **all forks are nil**, including `LondonBlock`. Without the `IsLondon` guard, someone could configure a chain with `ShanghaiTime` set but `LondonBlock = nil`. Shanghai's code assumes `header.BaseFee` exists (introduced by London). Without London, there is no base fee, and the code would panic.

The check ensures: **no matter how you configure the chain, if London isn't active, no post-London fork takes effect.** It's a defensive guarantee that the fork dependency chain cannot be broken.

## Q7: What is the `Rules` struct and why does it exist?

`Rules` is a **performance optimization**. It snapshots all fork activation flags into a flat struct of booleans at the start of each block.

**The problem:** The EVM may execute thousands of opcodes per transaction. Many opcodes need to check fork status. Without `Rules`, each check calls `IsShanghai()` which internally calls `IsLondon()`, performs nil checks, pointer dereferences, and numeric comparisons — repeated thousands of times with the same result (block number and timestamp don't change within a block).

**The solution:** Compute once at block start, read booleans thereafter:

```go
// Block start: compute once
rules := chainConfig.Rules(blockNum, isMerge, timestamp)

// During opcode execution: just read a bool
if rules.IsShanghai {  // single memory read, no function calls
    // ...
}
```

| | Without Rules | With Rules |
|---|---|---|
| Each check costs | method call -> nil check -> pointer deref -> comparison | read one bool |
| Thousands of checks per tx | repeat full computation | thousands of bool reads |

It converts repeated computation into a single table lookup.
