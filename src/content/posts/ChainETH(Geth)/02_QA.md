## Q1: Is AccessListTx (0x01) still needed if DynamicFeeTx (0x02) also has an AccessList field?

No. `DynamicFeeTx` (0x02) is a **superset** of `AccessListTx` (0x01) — it includes the `AccessList` field plus the EIP-1559 tip/fee-cap gas model. In practice, there is no reason to send a 0x01 transaction when 0x02 is available.

Later transaction types are also supersets: `BlobTx` (0x03) and `SetCodeTx` (0x04) both include `AccessList` + tip/fee-cap as well.

`AccessListTx` exists for **historical compatibility**. It was introduced in the Berlin fork (before London introduced 0x02). Transactions already on-chain are immutable — geth must be able to parse and execute 0x01 transactions forever.

## Q2: What do the blob-related fields in BlobTx mean?

Blob transactions (EIP-4844) create a separate data channel for rollups. A blob is 128 KB of raw data (4096 field elements × 32 bytes). Blobs are not accessible to the EVM, not stored permanently on-chain, and are deleted by nodes after ~18 days.

### `BlobFeeCap` — fee cap for blob data

Blob gas has its own fee market, independent of execution gas. Just as EIP-1559 introduced a base fee for execution gas, blobs have their own dynamically adjusted base fee.

- `GasFeeCap` / `GasTipCap` → control how much you pay for **execution** (EVM computation)
- `BlobFeeCap` → controls how much you pay for **blob data**

Each blob consumes 131,072 blob gas (2^17). A transaction with 3 blobs costs 3 × 131,072 = 393,216 blob gas. Total blob fee = blob gas × blob base fee. If the current blob base fee exceeds `BlobFeeCap`, the transaction won't be included.

### `BlobHashes` — versioned hashes of the blobs

Each hash is the identity of a blob, computed as:

```
BlobHash = 0x01 || SHA256(KZG_commitment)[1:]
           ^^^^
           version byte
```

These hashes are **included in the consensus encoding** (they affect the transaction hash). The EVM can access them via the `BLOBHASH` opcode. Rollup contracts use this to verify "this transaction actually carried the blob data I expected." However, the EVM can only see the hash — **not the actual blob content**.

### `Sidecar` — the actual blob data

```go
type BlobTxSidecar struct {
    Version     byte                 // Version
    Blobs       []kzg4844.Blob       // 128 KB each — the raw data
    Commitments []kzg4844.Commitment // 48 bytes each — cryptographic fingerprint of the blob
    Proofs      []kzg4844.Proof      // 48 bytes each — proves blob matches its commitment
}
```

The relationship between the three:

```
Blob (128KB raw data)
  │
  │  KZG polynomial commitment
  ▼
Commitment (48 bytes) ──→ SHA256 truncation ──→ BlobHash (32 bytes, stored in tx)
  │
  │  Generate proof
  ▼
Proof (48 bytes)      ──→ Verifies blob actually corresponds to this commitment
```

The sidecar is tagged `rlp:"-"` — it is **not part of the consensus encoding and does not affect the transaction hash**. The sidecar and the transaction body have different lifetimes:

- **Transaction body** (including BlobHashes) → stored permanently on-chain
- **Sidecar** (Blobs + Commitments + Proofs) → propagated on P2P network, kept ~18 days, then **deleted**

This is why blobs are cheap — the data does not permanently occupy full node disk space.

### Header fields

- **`BlobGasUsed`** — total blob gas consumed by all blob transactions in this block
- **`ExcessBlobGas`** — a cumulative value used to calculate the next block's blob base fee. More blob usage → excess rises → blob base fee increases. Same dynamic adjustment mechanism as EIP-1559 execution gas base fee, but for blob data.

## Q3: How is the sidecar data processed through its lifecycle?

### Stage 1: Entering the tx pool — Validation

When a blob transaction arrives (`core/txpool/validation.go:159`), three checks are performed:

```go
sidecar := tx.BlobTxSidecar()
if sidecar == nil {
    return errors.New("missing sidecar in blob transaction")        // 1. Must exist
}
sidecar.ValidateBlobCommitmentHashes(hashes)                        // 2. Commitment → hash match
kzg4844.VerifyBlobProof(&sidecar.Blobs[i], commitment, proof)      // 3. Cryptographic proof verification
```

1. Sidecar must not be nil
2. Recompute `SHA256(commitment)` and verify it matches each `BlobHash` in the transaction
3. KZG proof verification — cryptographically prove each blob corresponds to its commitment

Only after all checks pass is the transaction accepted into the pool.

### Stage 2: Blob Pool storage — on disk

Normal transactions live in memory (legacypool), but blob transactions are too large (one blob = 128KB, up to 6 = 768KB). The blob pool RLP-encodes the **entire transaction including sidecar** and writes it to disk (`core/txpool/blobpool/blobpool.go:1771`):

```go
blob, _ := rlp.EncodeToBytes(tx)   // serialize entire tx
id, _ := p.store.Put(blob)          // write to disk (using billy library)
```

Only lightweight metadata (nonce, fee, size) is kept in memory.

### Stage 3: Block building — separation

When the miner includes a blob transaction in a block (`miner/worker.go:320`), the sidecar is **stripped off**:

```go
sc := tx.BlobTxSidecar()                    // extract sidecar
txNoBlob := tx.WithoutBlobTxSidecar()       // transaction body (without sidecar)
env.txs = append(env.txs, txNoBlob)         // tx body → goes into block
env.sidecars = append(env.sidecars, sc)      // sidecar → collected separately
```

The transaction written to the blockchain database **does not contain the sidecar**. The sidecar is returned separately to the CL (consensus layer), which is responsible for propagating it on the P2P network.

### Stage 4: Broadcasting — also stripped

When the blob pool broadcasts new transaction events, sidecars are also stripped (`core/txpool/blobpool/blobpool.go:1696`):

```go
adds = append(adds, tx.WithoutBlobTxSidecar())
p.discoverFeed.Send(core.NewTxsEvent{Txs: adds})
```

### Summary flow

```
Blob transaction arrives
    │
    ▼
Validate sidecar (KZG proof, commitment-hash match)
    │
    ▼
Blob Pool (entire tx with sidecar stored on disk)
    │
    ▼
Miner builds block ──→ Separation
    │                       │
    ▼                       ▼
Transaction body         Sidecar
(into block,             (returned to CL,
 permanent storage)       P2P propagation,
                          ~18 days then deleted)
```

The key design: **the sidecar is stripped after validation but before going on-chain**. Only `BlobHashes` (32 bytes each) are stored on-chain, not the 128KB blob data. This is the fundamental reason blobs are cheaper than calldata.
