## Q1: What is ethdb and LevelDB?

**`ethdb`** is a set of key-value store interfaces defined by geth that abstract away the underlying database implementation. The core interfaces live in `ethdb/database.go`:

- `KeyValueReader` — `Has(key)`, `Get(key)`
- `KeyValueWriter` — `Put(key, value)`, `Delete(key)`
- `KeyValueStore` — composite of Reader + Writer + Batcher + Iteratee + Compacter + Closer
- `Database` — `KeyValueStore` + `AncientStore` (for cold/archived data)

**LevelDB** (`ethdb/leveldb/leveldb.go`) is one concrete implementation. It is a Google-developed embedded key-value database using an LSM-Tree architecture: writes go to an in-memory memtable first, then flush to sorted on-disk SSTables, with background compaction. It is well-suited for blockchain workloads (append-heavy writes + key lookups).

The LevelDB wrapper is thin — most methods delegate directly to the underlying `leveldb.DB`. The one exception is `DeleteRange()`: since LevelDB has no native range-delete, geth manually iterates keys and deletes them in batches (up to 10,000 per call).

There are also two other backends:
- **Pebble** (`ethdb/pebble/pebble.go`) — CockroachDB's LevelDB replacement, better performance, native `DeleteRange` support, and the default in newer geth versions.
- **MemoryDB** (`ethdb/memorydb/`) — an in-memory `map[string][]byte` for testing.

Upper layers (`BlockChain`, `rawdb`) only depend on the `ethdb` interfaces, never on a specific backend.

## Q2: Does Pebble need to be installed separately?

No. Pebble is a **pure Go library** (`github.com/cockroachdb/pebble v1.1.5`), declared as a dependency in `go.mod`. When you `go build`, the Go toolchain automatically fetches and compiles it, linking it directly into the geth binary.

Like LevelDB, Pebble is an **embedded database** — no separate server process, no installation, no ports. It is just a Go package that becomes part of the geth process after compilation.

The code in `ethdb/pebble/pebble.go` is geth's **wrapper layer** that adapts Pebble's API to the `ethdb.KeyValueStore` interface. The actual database engine lives in the external `github.com/cockroachdb/pebble` module.

## Q3: Where does Pebble store its data on disk?

Data is stored in the **geth data directory** under `chaindata/`. The full path is:

```
<datadir>/geth/chaindata/
```

Default `<datadir>` by OS:
- Linux: `~/.ethereum`
- macOS: `~/Library/Ethereum`
- Windows: `%APPDATA%\Ethereum`

The call chain:

```
eth/backend.go
  stack.OpenDatabaseWithOptions("chaindata", ...)       // name = "chaindata"
    -> node.ResolvePath("chaindata")                    // resolves to <datadir>/geth/chaindata
      -> openKeyValueDatabase(directory: "...chaindata")
        -> pebble.New(file, ...)                        // file = that directory path
          -> pebble.Open(file, opt)                     // Pebble creates SST files, WAL, etc. here
```

Pebble (and LevelDB) create WAL (write-ahead log) files, SST files (sorted string tables), and MANIFEST files inside this directory. You can customize the path with the `--datadir` flag when starting geth.

## Q4: Why does geth still have a `consensus/` package if it's just the execution layer?

`eth/catalyst` and `consensus/` have completely different responsibilities:

- **`eth/catalyst`** = communication layer. It receives JSON-RPC calls from the CL client (`engine_newPayload`, `engine_forkchoiceUpdated`, etc.) and forwards instructions to internal components.

- **`consensus/`** = validation rules. Whenever geth receives a block (whether from CL or via sync), it needs to **locally verify** that the block header is valid. This includes:
  - `VerifyHeader()` — are header fields correct (timestamp, gas limit, base fee calculation, difficulty == 0, etc.)?
  - `Finalize()` — post-transaction state modifications (e.g., processing withdrawals by crediting validator accounts)
  - `FinalizeAndAssemble()` — during block building, assemble the final block with withdrawals root, etc.
  - `Prepare()` — fill in consensus-related header fields when building a new block

The EL does not blindly trust data from the CL — it independently validates every block header using the rules in `consensus/beacon`.

In short: **catalyst is "what did the CL tell me", consensus is "how do I verify it's correct"**.

## Q5: Is all the execution layer's validation logic in the `consensus/` package?

No. `consensus/` only handles **header-level consensus rule validation**. The EL's validation is split across four layers:

| What | Where | Checks |
|------|-------|--------|
| Header consensus rules | `consensus/beacon/` | timestamp, gas limit, base fee calculation, difficulty==0, withdrawals hash, etc. |
| Block body integrity | `core/block_validator.go` -> `ValidateBody()` | tx merkle root matches header, uncles are empty (post-PoS), block size limits (EIP-7934), etc. |
| State execution result | `core/block_validator.go` -> `ValidateState()` | after executing all txs: gas used, receipt root, bloom filter, state root all match header claims |
| Individual transactions | `core/txpool/validation.go` -> `ValidateTransaction()` | signature, nonce, balance, gas limit, EIP-1559 fee parameters, blob tx format, etc. |

Their order during `InsertChain()`:

```
InsertChain()
  1. engine.VerifyHeader()        <- consensus/ checks header format
  2. validator.ValidateBody()     <- core/ checks body matches header
  3. StateProcessor.Process()     <- core/ executes each transaction (EVM)
  4. validator.ValidateState()    <- core/ checks execution results match header claims
```

## Q6: Where is the block header computed/produced?

The header is built in **two phases**, both in `miner/worker.go`:

### Phase 1: Before executing transactions — `prepareWork()` (line 206)

Creates a "half-finished" header with known fields:

```go
header := &types.Header{
    ParentHash: parent.Hash(),
    Number:     new(big.Int).Add(parent.Number, common.Big1),
    GasLimit:   core.CalcGasLimit(parent.GasLimit, miner.config.GasCeil),
    Time:       timestamp,
    Coinbase:   genParams.coinbase,
}
```

Then fills in additional fields:
- **BaseFee** <- `eip1559.CalcBaseFee(parent)` — calculated from parent's gas usage
- **MixDigest** <- RANDAO randomness from CL
- **ExcessBlobGas** <- `eip4844.CalcExcessBlobGas(parent)` — from parent's blob gas
- **ParentBeaconRoot** <- beacon block root from CL
- Calls `engine.Prepare()` for final consensus adjustments

At this point **GasUsed, StateRoot, ReceiptHash, TxHash, Bloom** are all zero — transactions haven't been executed yet.

### Phase 2: After executing transactions — `generateWork()` -> `FinalizeAndAssemble()` (line 165)

1. `fillTransactions()` pulls txs from the pool, executes each through the EVM, accumulates receipts and gas used
2. Collects requests (deposits, withdrawal queue, consolidations), computes `RequestsHash`
3. Calls `engine.FinalizeAndAssemble()`, which:
   - Processes withdrawals (credits validator accounts)
   - Computes **StateRoot** from the post-execution state
   - Computes **ReceiptHash** and **Bloom** from receipts
   - Computes **TxHash** from the transaction list
   - Assembles the complete `Block`

The header is not computed all at once — **deterministic fields are filled first, then execution-dependent fields are back-filled after running all transactions**.

## Q7: Explain the four Go patterns used across the codebase

### Pattern 1: Lifecycle Interface

**Problem:** Geth has dozens of subsystems that need to be started and stopped in order. If each one had a different start/stop mechanism, managing them would be chaotic.

**Solution:** A unified contract — all subsystems must implement `Start()` and `Stop()`:

```go
type Lifecycle interface {
    Start() error
    Stop() error
}
```

`Node` (the service host) maintains a `[]Lifecycle` slice. Subsystems register via `RegisterLifecycle()`. On `Node.Start()`, all are started in registration order. On `Node.Close()`, they are stopped in **reverse order** — because later subsystems depend on earlier ones (e.g., stopping the database before the tx pool would crash the tx pool).

If any subsystem fails to start, only the already-started ones are stopped (in reverse).

### Pattern 2: Event Feed

**Problem:** When a new block is inserted, the tx pool, miner, and P2P handler all need to know. But `core/` (blockchain) must not import `eth/` (handler) or `miner/` — that would create circular dependencies.

**Solution:** Publish/subscribe via `event.Feed`. The lower layer sends events; upper layers subscribe:

```go
// Publisher (blockchain): after inserting a block
chainHeadFeed.Send(ChainHeadEvent{Header: newHeader})

// Subscriber (tx pool, miner, handler): registered earlier
ch := make(chan ChainHeadEvent, 10)
sub := chainHeadFeed.Subscribe(ch)
```

The blockchain does not know or care who is listening. Each subscriber reacts independently. This keeps layers decoupled.

### Pattern 3: Config Struct

**Problem:** Each subsystem has many configurable parameters (cache size, gas price, database path, etc.) coming from different sources (CLI flags, TOML config files, code defaults).

**Solution:** Each subsystem defines a `Config` struct with all its parameters, plus a `Defaults` variable with production defaults. The constructor takes the config as a parameter. The CLI layer (`cmd/geth/`) maps flags to config fields.

This separates concerns: subsystems only know about Config structs, CLI only knows about mapping flags, and tests can construct configs directly without simulating a command line.

### Pattern 4: Atomic Pointer for Hot State

**Problem:** `currentBlock` (the chain head) is read by nearly every goroutine — RPC queries, tx pool validation, sync checks, P2P broadcast. But it is written very rarely (only when a new block is inserted). Using a mutex would force all readers to queue up for a lock, creating a bottleneck.

**Solution:** Use `atomic.Pointer[T]` — a lock-free, concurrency-safe pointer:

```go
currentBlock atomic.Pointer[types.Header]
```

- **Read:** `currentBlock.Load()` — any goroutine, any time, no lock, no waiting
- **Write:** `currentBlock.Store(newHeader)` — atomically swaps the pointer to a brand-new header object

"Atomic" means the swap is indivisible at the CPU instruction level. Readers see either the old header or the new header, never a half-written state.

**Limitation:** Only suitable for whole-object replacement. You cannot modify a single field of the header — you must create a new header and swap the entire pointer.

## Q8: In Pattern 1, what is `Node` and why does start/stop order matter?

`Node` is geth's **service host** — a container/manager. It does no Ethereum business logic itself. Its job is:
1. Start the P2P server (networking)
2. Start the RPC server (external API)
3. Manage the lifecycle of all registered subsystems

Inside `Node` (`node/node.go:60`):

```go
lifecycles []Lifecycle  // All registered backends, services, and auxiliary services
```

**Why order matters — a concrete example:**

Registration order: `Database -> TxPool -> Syncer`

Dependencies:
- Syncer depends on TxPool (notifies pool after syncing new blocks)
- TxPool depends on Database (queries account balances during validation)

Start in registration order (dependencies come first):
```
Start:  Database -> TxPool -> Syncer
        ready       ready      ready, all deps available
```

Stop in reverse order (dependents stop first):
```
Stop:   Syncer -> TxPool -> Database
        stops      stops     stops last, no one using it anymore
```

If you stopped the Database first, TxPool would crash trying to query it, and Syncer would crash trying to notify TxPool.

**Error handling** (`node/node.go:190-199`): if a subsystem fails to start, only the already-started ones are stopped in reverse — `Stop()` is never called on something that was never started.

## Q9: In Pattern 4, we create a new header and just point to it?

Yes. The operation works like this:

```
Before:   currentBlock pointer --> [Old Header: block #100]

After Store(newHeader):

          currentBlock pointer --> [New Header: block #101]

                                   [Old Header: block #100]  <- GC reclaims when no references remain
```

The old header object is not modified or destroyed. The pointer just changes direction instantly. Goroutines that already called `Load()` and got the old header keep using it safely — they hold their own reference. Only the next `Load()` call returns the new header.

## Q10: What if a goroutine reads the stale (old) header?

In practice, there is virtually no impact. Two reasons:

**1. The staleness window is extremely short.** `Store()` and `Load()` are single CPU instructions. A goroutine can only read the old header in the nanosecond before `Store()` executes. The very next `Load()` returns the new value.

**2. A stale read is "slightly outdated", not "wrong":**

| Caller | Effect of reading stale header |
|--------|-------------------------------|
| RPC `eth_blockNumber` | Returns 100 instead of 101; next request is correct |
| TxPool validating nonce/balance | Validates against block #100 state, which is still valid |
| Syncer checking "am I behind?" | Thinks head is #100, off by one block; corrected on next check |
| Miner checking parent | CL specifies the correct parent via `forkchoiceUpdated` anyway |

In all cases, a stale read means "learned about a block one moment late" — never data corruption or logic errors. For operations that truly need strict ordering with writes, geth uses Event Feed (Pattern 2) to guarantee sequencing, not repeated `Load()` polling.
